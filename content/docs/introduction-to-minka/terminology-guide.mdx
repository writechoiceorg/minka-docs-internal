This guide establishes consistent terminology and capitalization rules for all Minka documentation. Use this guide when writing, reviewing, or translating documentation to ensure consistency across all materials and languages.

## Purpose

This guide serves as:

- **Internal reference** for documentation contributors
- **Translation guideline** for maintaining consistency across languages
- **Style standard** for automated checks and linting
- **Foundation** for a future public glossary

---

## Core Ledger Concepts

### Anchor

**Definition**: A core Ledger record that securely links a public alias (such as a phone number or email) to a specific payment credential (such as a bank account). Anchors are the foundational records that enable the Alias Directory.

**Capitalization**:

- **Capitalize** when referring to the Ledger record type: "An Anchor record", "create an Anchor", "the Anchor's target field"
- **Lowercase** only in code examples, field names, or technical references: `anchor.read()`, `data.anchor`, `POST /v2/anchors`

**Contexts**:

- Use "Anchor" when explaining the concept or record type
- Use "anchor record" when emphasizing it's a record in the Ledger
- Use "anchor" (lowercase) in code, API endpoints, and field names

**Translation**:

- **Keep in English** for technical accuracy
- If translation is required, use the local equivalent of "anchor" (e.g., "ancla" in Spanish) but maintain capitalization rules

---

### Alias

**Definition**: A human-readable identifier (such as a phone number, email address, or ID number) that maps to a financial account. An alias is stored in the `source` field of an Anchor record.

**Capitalization**:

- **Capitalize** when part of a product or feature name: "Alias Directory", "Alias Handle", "Alias Directory Overview"
- **Lowercase** when referring to the general concept: "an alias", "the alias", "create aliases", "alias resolution"
- **Lowercase** in code examples and field names: `alias-handle`, `POST /v2/advices/alias-resolve`

**Contexts**:

- Use lowercase "alias" when describing what it is conceptually
- Use capitalized "Alias" only in specific product names or titles
- Use "alias handle" (lowercase) when referring to the identifier itself
- Use "Alias Handle" (capitalized) when it's a formal term in a title or heading

**Translation**:

- **Translate** the general concept: "alias" → "alias" (Spanish), "pseudonyme" (French)
- **Keep in English** for product names: "Alias Directory" remains "Alias Directory"
- **Keep in English** for technical terms: "alias handle" → "alias handle" (not translated)

### Handle

**Definition**: A unique identifier for a Ledger record. Handles are globally unique across all Domains and record types. Examples include `wallet:user-123`, `tel:+15551234567`, or `anchor-for-melissa-ruiz`.

**Capitalization**:

- **Lowercase** in all contexts: "the handle", "a unique handle", "handle uniqueness"
- **Capitalize** only when part of a compound term that is itself capitalized: "Alias Handle" (when used as a formal term in titles)

**Contexts**:

- Use lowercase "handle" when referring to the identifier concept
- Use "handle" when describing uniqueness: "handles are globally unique"
- Use "handle" in code examples: `<alias-handle>`, `handle: "wallet:user-123"`
- Use "Alias Handle" or "Wallet Handle" when these are formal terms in headings or titles

**Translation**:

- **Translate** the general concept: "handle" → "identificador" (Spanish), "identifiant" (French)
- **Keep in English** for technical compound terms: "alias handle" → "alias handle"
- **Keep in English** in code examples and placeholders

### Record

**Definition**: A data structure stored in the Ledger. All core concepts (Anchors, Wallets, Intents, etc.) are stored as records.

**Capitalization**:

- **Lowercase** when used generically: "a record", "the record", "Ledger records"
- **Capitalize** only when part of a compound term that is itself a proper noun: "Ledger record" (when "Ledger" is capitalized)

**Contexts**:

- Use lowercase "record" when referring to the general concept
- Use "Ledger record" (capitalize Ledger, lowercase record) when emphasizing it's a record in the Ledger
- Use "record" in code examples and technical references

**Translation**:

- **Translate** the general concept: "record" → "registro" (Spanish), "enregistrement" (French)
- **Keep compound terms**: "Ledger record" → "registro del Ledger" (translate record, keep Ledger)

**Capitalization**:

- **Capitalize** when referring to the platform: "the Ledger", "Minka Ledger", "Ledger API", "Ledger record"

## Technical Terms

### Hash

**Definition**: A cryptographic fingerprint of a record. The hash is generated from the record's data and is used to verify integrity and create digital signatures.

**Capitalization**:

- **Lowercase** in all contexts: "the hash", "hash value", "hash field"
- **Lowercase** in code examples: `hash: "abc123"`, `data.hash`

**Contexts**:

- Use lowercase "hash" in all contexts
- Use "hash" when referring to the cryptographic concept
- Use "hash" in code examples and field names

**Translation**:

- **Keep in English** for technical accuracy: "hash" → "hash"
- If translation is required, use the local equivalent but keep it lowercase

---

### LUID (Ledger Unique Identifier)

**Definition**: A unique identifier assigned by the Ledger to each record. Format: `$anc.123...` for Anchors, `$wlt.123...` for Wallets, etc.

**Capitalization**:

- **Uppercase** when using the acronym: "LUID", "the LUID"
- **Lowercase** in code examples and field names: `luid: "$anc.123"`, `data.luid`
- **Capitalize** when spelling out: "Ledger Unique Identifier"

**Contexts**:

- Use "LUID" (uppercase) when using the acronym
- Use "luid" (lowercase) in code examples and field names
- Use "Ledger Unique Identifier" when spelling out the full term

**Translation**:

- **Keep in English**: "LUID" → "LUID", "Ledger Unique Identifier" → "Ledger Unique Identifier"

---

## Status and State Terms

### Status Values

**Definition**: Values that indicate the current state of a record (e.g., `active`, `suspended`, `cancelled` for Anchors; `pending`, `accepted`, `prepared`, `committed`, `completed`, `aborted`, `rejected` for Intents).

**Capitalization**:

- **Lowercase** in all contexts: "status is `active`", "the `suspended` status", "status: `pending`"
- **Lowercase** in code examples: `status: "active"`, `meta.status`

**Contexts**:

- Always use lowercase for status values
- Use backticks when referring to specific status values: `active`, `suspended`
- Use "status" (lowercase) when referring to the concept

**Translation**:

- **Translate** status values: "active" → "activo" (Spanish), "actif" (French)
- **Keep in English** in code examples and API responses

## Field Names and API Terms

### Field Names

**Capitalization**:

- **Lowercase** for all field names: `handle`, `target`, `source`, `custom`, `hash`, `luid`, `meta`
- **Use backticks** when referring to field names in documentation: "the `handle` field", "set `target` to the account"

**Contexts**:

- Always use lowercase for field names
- Use backticks to distinguish field names from regular text
- Use "field" (lowercase) when referring to the concept

**Translation**:

- **Keep in English** for field names: `handle` → `handle`, `target` → `target`
- Field names are not translated in code or API documentation

### API Endpoints

**Capitalization**:

- **Capitalize HTTP methods**: `GET`, `POST`, `PUT`, `DELETE`

**Contexts**:

- Use lowercase for endpoint paths: `/v2/anchors`, `/v2/intents/:handle`
- Capitalize HTTP methods: `POST /v2/anchors`
- Use backticks for code formatting

**Translation**:

- **Keep in English**: API endpoints are not translated

## Translation Guidelines

### Terms to Keep in English

Always keep these terms in English, regardless of language:

- Product names: "Minka Ledger", "Alias Directory"
- Core concepts: "Anchor", "Wallet", "Symbol", "Domain", "Intent", "Bridge", "Signer", "Circle", "Policy"
- Technical terms: "handle", "hash", "luid", "schema"
- API endpoints and field names
- Status values in code examples (translate in descriptive text)

### Terms to Translate

Translate these terms to the target language:

- General descriptive terms: "record", "account", "balance", "transaction"
- Status values in descriptive text (keep English in code)
- Common verbs and actions: "create", "update", "retrieve", "delete"

### Translation Format

When translating:

1. **Keep English terms** for core concepts and technical terms
2. **Translate descriptive text** around the technical terms
3. **Maintain capitalization rules** even in translated text
4. **Keep code examples** in English with English placeholders

**Example (Spanish)**:

- English: "Create an Anchor to link an alias to a payment credential"
- Spanish: "Crea un Anchor para vincular un alias a una credencial de pago"
  - "Anchor" stays in English (core concept)
  - "alias" stays in English (technical term)
  - Descriptive words are translated
