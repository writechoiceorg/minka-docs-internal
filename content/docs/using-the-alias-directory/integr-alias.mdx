This tutorial guides you through the process of integrating your Alias Directory solution with a Centralized Directory (such as a specific regional registry like DICE, or a national registry). Regulated Real-Time Payment (RTP) environments require this integration to ensure third-party validation and compliance for all alias operations.

## Prerequisites
    Before implementing this integration flow, make sure you have the following in place:

    - **API Access:** You have the base URL for the Anchors API `/v2`
    - **Bridge Configuration:** You have a configured Bridge record that connects your Ledger to the external Centralized Directory service.
    - **Signer Setup:** You have an authenticated **Signer** (a cryptographic key pair that represents your identity and authorizes operations on the ledger) with permissions to perform `POST` and `GET` operations on Anchor records.
    - **Regulatory Knowledge:** You understand the data requirements (e.g., owner data, account data) and timestamp requirements of the external Centralized Directory.

## Integration via API and CLI

<Tabs items={["API", "CLI"]}>
  <Tab value="API">
    When you create a new alias in a regulated environment, the Ledger performs a necessary third-party validation step before confirming the alias registration.

<Steps>
    <Step>
    ### Submit the Anchor Creation Request
        You initiate the process by submitting the new Anchor record via the standard creation endpoint `POST /v2/anchors`. The request must include all required fields for the Centralized Directory, including custom data and compliance information.
    </Step>
     <Step>
     ### Third-Party Validation (Ledger Action)

     Upon receiving your request, the Ledger automatically manages the third-party integration workflow:

     1. The Ledger uses the configured Bridge to forward the alias details to the Centralized Directory (e.g., DICE) for validation.
     2. The Centralized Directory validates the submitted account and user data.
     3. If the validation is successful, the Ledger adds compliance-required Timestamps to the Anchor record, fulfilling regulatory mandates.
     4. The Ledger completes the Anchor registration and returns a success status to your system.
    </Step>
    </Steps>

## Flow 2: Alias Lookup and Resolution
    Alias lookups (resolution) must prioritize local data access while ensuring you can still resolve payments for accounts registered in the centralized system.

    <Steps>
        <Step>
     ### Submit the Lookup Request
        You submit the resolution request using the Alias Key (`:handle`) using the endpoint `GET /v2/anchors/:handle`
        </Step>
        <Step>
     ### Local-First Check

        The Ledger executes a local-first check to resolve the alias as quickly as possible:

            1. The Ledger first attempts to find the matching Anchor record in your local, federated Ledger environment.

            2. If the alias is found locally and is `ACTIVE`, the Ledger immediately returns the Payment Credential.
            
            3. If the alias is not found locally, the Ledger automatically uses the Bridge to look for it in the Centralized Directory. This is crucial for mapping Aliases that exist in DICE but not in the Federated Directory.
        </Step>
        <Step>
        
    ### Final Resolution
            If the Centralized Directory successfully resolves the alias, the Ledger retrieves the data and returns the full Anchor details to your system, completing the lookup.
        </Step>
        </Steps>

## Compliance Requirements: Third-Party Timestamps
    In environments with a Centralized Directory, you require timestamps as part of the integration, and they are essential for compliance and auditability.

    - **Purpose:** The Ledger adds timestamps (such as R101 or C110) to the Anchor record during the creation and update flows to provide a verifiable record of the moment regulatory checks or updates occurred.
    - **Mechanism:** The Ledger automatically adds these timestamps upon successful third-party validation, ensuring that the final Anchor record meets the requirements of the Centralized Directory.
    - **Audit Trail:** These timestamps establish an immutable audit trail for compliance purposes.
  </Tab>
  
  <Tab value="CLI">
    Use the Minka CLI to create and look up aliases in a centralized directory environment. The CLI automatically handles the integration workflow, including third-party validation.

    <Steps>
      <Step>
        ### Create an Alias with Centralized Directory Integration
        
        Create a JSON file with the anchor data including all required fields for the Centralized Directory:

        ```json
        {
          "handle": "<alias-value>",
          "target": "<target-account>",
          "custom": {
            "aliasType": "PHONE",
            "documentType": "NIDN",
            "documentNumber": "<document-number>",
            "accountType": "<account-type-standard-value>",
            "accountNumber": "<account-number>",
            "firstName": "<firstname>",
            "lastName": "<lastname>",
            "entityType": "individual"
          },
          "access": [
            { "action": "any", "signer": { "$record": "owner" } }
          ],
          "schema": "person"
        }
        ```

        Use the `minka anchor create` command to submit the alias:

        ```bash
        minka anchor create \
        --file new-alias.json \
        --signer <your-signer-handle> \
        --label "nidn:<document-number>" \
        --status "ACTIVE"
        ```

        The Ledger automatically handles third-party validation through the configured Bridge and adds compliance-required timestamps.
      </Step>
      
      <Step>
        ### Look Up an Alias (Local-First Resolution)
        
        Use the `minka anchor show` command to look up an alias. The CLI automatically performs local-first resolution and falls back to the Centralized Directory if needed:

        ```bash
        minka anchor show <alias-handle>
        # Example: minka anchor show <alias-value>
        ```

        The CLI constructs the request and uses your configured Signer credentials for authentication. The Ledger automatically:
        1. Checks the local federated directory first
        2. Falls back to the Centralized Directory via the Bridge if not found locally
        3. Returns the complete anchor record with all metadata and timestamps
      </Step>
    </Steps>
    
    <Callout>
      The CLI automatically handles the integration workflow with the Centralized Directory. You don't need to manually manage Bridge connections or timestamp requirements—the Ledger handles these automatically.
    </Callout>
  </Tab>
</Tabs>
