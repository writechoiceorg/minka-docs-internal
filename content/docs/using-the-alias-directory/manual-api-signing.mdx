This guide provides the low-level, manual process for hashing and signing Minka Ledger API requests. You must follow these steps if you are building a custom integration directly against the REST API in a language other than Node.js (e.g., Python, Go, Java).

<Callout type="warn" title="For Advanced Integrations Only">
This is an advanced guide. These steps are complex, and any error will result in a failed request.

If you [sign requests using the SDK or CLI](/docs/using-the-alias-directory/sign-requests), all of these steps are handled for you automatically. We strongly recommend using our official tools whenever possible.
</Callout>

## Pre-requisites
- **Ed25519 Signing:** To create a signature from your private key.
- **SHA-256 Hashing:** To create the data hash and signature digest.
- **Canonical JSON (RFC 8785):** A JSON serializer that sorts all object keys alphabetically before outputting the string. This is critical for creating a reproducible, deterministic hash.

## Manual API Signing Steps

Creating a valid proof for a request (like `POST /v2/wallets`) is a deterministic, three-step process.

<Steps>
    <Step title="Create the Data Hash">
    First, you must create a unique, verifiable hash of the data object (the main payload of your request).

    1. **Serialize the `data` Object:** The JSON serialization must follow the RFC 8785 standard. The most critical rule is that all object properties must be sorted alphabetically by key.
    2. **Hash the Serialized Data:** Use the SHA-256 algorithm on the serialized string. The resulting hash should be a `hex` encoded string.
    
    This dataHash is the value for the top-level hash field in the request body.
    </Step>
    
    <Step title="Create the Signature Digest">
    You do not sign the `dataHash` directly. Instead, you create a second hash, called a "digest." This digest includes the `dataHash` and any custom data you want to add to the proof itself (like a timestamp).
    This process, known as double hashing, ensures the integrity of the proof's custom data.

    1. Get the `dataHash` from Step 1.
    2. Get the `signatureCustom` object. This is the JSON object you will place inside the `meta.proofs[n].custom` field. If you have no custom proof data, use an empty string.
    3. Serialize the `signatureCustom` data using the same RFC 8785-compliant serializer.
    4. Concatenate the `dataHash` and the serialized `signatureCustom` data into a single string.
    5. Hash the concatenated string using SHA-256. The result (as hex) is your `signatureDigest`.
    </Step>
        
    <Step title="Sign the digest">
    Finally, you sign the `signatureDigest` (from Step 2) using your Ed25519 private key.
    
    1. Convert the `signatureDigest` (which is a hex string) into a Buffer or byte array.
    2. Sign the buffer using your private key.
    3. Encode the final signature as a base64 string. This is the result for your proof.    
    </Step>
</Steps>

## Signed Request Structure
A fully formed request body sent to a mutation endpoint (like `POST /v2/wallets`) includes the `data` payload, its hash (from Step 1), and the `meta.proofs` object you just generated.

### Proof Object Fields
- `hash`: The dataHash of the main data object (from Step 1).
- `data`: The JSON payload for the new record.
- `meta.proofs`: An array of proof objects. Each object represents one signature and contains:
  - `method`: The signature method used (e.g., "ed25519-v2").
  - `public`: The public key (in base64) used for verification.
  - `digest`: The double-hashed signatureDigest (from Step 2).
  - `result`: The final base64-encoded signature of the digest (from Step 3).
  - `custom`: The JSON object of data that was included in the digest (from Step 2).

## Troubleshooting
If you receive a signature or hash error (such as `crypto.hash-invalid` or `crypto.signature-invalid`), check the following:

- **Canonical JSON:** Ensure your `data` object (for Step 1) and your `signatureCustom` object (for Step 2) are both serialized using RFC 8785 (alphabetical keys) before hashing.

- **Digest Content:** Confirm your `signatureDigest` (Step 2) is a hash of the `dataHash` (Step 1) concatenated with the serialized `signatureCustom` data.

- **Signed Target:** Ensure your `result` (Step 3) is a signature of the `signatureDigest`, not a signature of the raw `dataHash`.
