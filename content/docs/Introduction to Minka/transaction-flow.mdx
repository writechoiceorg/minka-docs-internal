This page explains how a transaction moves through the Minka platform, from its initiation by a user to its final settlement in a ledger. Understanding this flow helps you see how Minka's packaged solutions (Channels, Rails, Gateway, and Ledger) work together to create a complete payment network.

The flow generally follows four stages:
- **Origination (Minka Channels):** A user initiates the payment (e.g., via QR code or alias) using Minka Channels.
- **Network Processing (Minka Rails):** The transaction is sent to a network operator (like an ACH or Central Bank) that uses Minka Rails to manage the core network.
- **Intermediary Routing (Minka Gateway):** A participant bank or institution uses Minka Gateway to receive the transaction from the network and route it to the correct destination.
- **Final Settlement (Minka Ledger):** The destination's Minka Ledger records the transaction, acting as the ultimate system of record.

## Prerequisites
This conceptual guide assumes you are familiar with Minka's core solutions. For a detailed breakdown of each component, please read the [Minka Solutions](./minka-solutions.mdx) page first.

The flow is divided into two main phases:
### Phase 1: Alias Look-up
The first phase is the Alias Look-up. Before a payment is sent, the user's application (Minka Channels) must confirm the recipient. This request travels from Channels to the Minka Rails network, which routes the query to the correct participant bank's Minka Gateway.

The Gateway then checks its internal Minka Ledger to validate the recipient. Once confirmed, the system passes the 'Recipient Info' all the way back up this chain to the user's application.

### Phase 2: Payment
Once the recipient is confirmed, the user initiates Phase 2, the Payment, by creating a transaction Intent. This action triggers a two-phase commit orchestrated by Minka Rails to ensure the transaction is atomic (meaning it either fully succeeds or fully fails).

Rails first instructs all parties to enter a Prepare phase, where the system holds funds and validates accounts. After all parties report back that they are ready, Rails issues the Commit command.

The Gateway forwards this to the Minka Ledger for final settlement. The system then sends a confirmation back up the chain to notify the user that the transaction is complete.

## Roles 
The product flow highlights two distinct roles for institutions within the ecosystem: 

### Provider
A Provider is responsible for the core network infrastructure, such as a central bank or ACH operator. Their responsibilities include:
    - Ensuring the network can communicate with any centralized systems.
    - Connecting to local channels.
    - Testing and processing both credits and debits.

### Participant
A Participant is a member of the network, such as a bank, that connects to the provider's infrastructure. Their role is to:
    - Testing connections to channels.
    - Processing debits received from the network. 

## Tools and Components
While the diagram shows the high-level flow between packaged products, several underlying tools are required to make this flow functional. These include:
    - **Bridges:** Most Minka Ledgers are not standalone. They use Bridges to connect to other services, such as legacy bank cores or external centralized directories.
    - **Security:** A universal transaction flow requires security protocols to be in place. Ledger components like Circles and Policies handle this by defining permissions and access rules.
    - **CLI/SDK:** You use tools like the Minka CLI or SDKs to build, test, and integrate with this transaction flow.
