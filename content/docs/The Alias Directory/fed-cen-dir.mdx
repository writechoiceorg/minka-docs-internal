---
title: Federated and Centralized Alias Directories
---

When operating a Real-Time Payment (RTP) system, you must implement a strategy for managing alias-to-account linkages. The Minka Ledger supports two primary models for directory management: the Federated Directory model, where participant institutions manage their own alias records locally, and the Centralized Directory model, which involves integration with a single, third-party national registry.

## The Federated Directory Model

The Federated Directory model places the responsibility for alias creation and maintenance directly within the Minka Ledger environment controlled by the participant institution.

In this model, the alias records are registered and governed locally:

- **Local Management:** You manage your own alias records using Anchors within your Minka Ledger.
- **Decentralized Data:** Each participating institution creates and manages the alias linkages for its own users.
- **Benefits:** This model offers participants full control and flexibility over the alias lifecycle, security policies, and custom data fields related to their customers.

You use the standard Ledger API calls to manage these records, which are then available to other connected participants within the Minka ecosystem.

## The Centralized Directory Model
The Centralized Directory model involves integrating your system with an external, authoritative, third-party registry that maintains a single, comprehensive alias database for a regulated region.

- **Third-Party Authority:** This model is typically required within regulated RTP environments (like the environment the Alias Directory solution for SERVIBANCA is designed for in Colombia).
- **Integration Point:** You integrate the Minka Ledger with the Centralized Directory, such as DICE (Digital Identity and Credentials Ecosystem) or a system operated by a national entity like the Banco de la República.
- **Co-existence:** The Centralized Directory acts as the single source of truth for payment resolution across the entire nation or network. Your local, federated records must often be mapped to, or validated against, this central registry.

## Co-existence and Mapping

In many regulated environments, the two models must co-exist. The Minka Ledger is designed to handle this co-existence by managing the local Federated Directory while providing integration mechanisms for a Centralized Directory.

You must handle scenarios where an alias exists in one system but not the other, or where the central system (like DICE) must validate the creation or lookup of a local Anchor record.

This complex interaction ensures that:

- Your local system (Federated Directory) remains fast and authoritative for your customers.
- All transactions comply with the rules and data requirements of the national Centralized Directory.
