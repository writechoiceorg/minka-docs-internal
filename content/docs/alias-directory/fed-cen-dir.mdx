---
title: Federated and Centralized Alias Directories
---

When operating a Real-Time Payment (RTP) system, you must implement a strategy for managing alias-to-account linkages. The Minka Ledger supports two primary models for directory management, these are:

- Federated Directory
- Centralized Directory 

See the sections below for more details of each of the models.

## The Federated Model

The Federated Directory model places the responsibility for alias creation and maintenance directly within the Minka Ledger environment controlled by the participant institution. This model offers the following benefits:

- **Local Management:** You manage your own alias records using Anchors within your Minka Ledger.
- **Decentralized Data:** Each participating institution creates and manages the alias linkages for its own users.
- **Full Control:** This model offers participants full control and flexibility over the alias lifecycle, security policies, and custom data fields related to their customers.

You use the standard Ledger API calls to manage these records, which are then available to other connected participants within the Minka ecosystem.

## The Centralized Model

The Centralized Directory model involves integrating your system with an external, authoritative, third-party registry that maintains a single, comprehensive alias database for a regulated region.

- **Third-Party Authority:** This model is typically required within regulated RTP environments 
- **Integration Point:** You integrate the Minka Ledger with the Centralized Directory, such as DICE or a system operated by a national entity.
- **Co-existence:** The Centralized Directory acts as the single source of truth for payment resolution across the entire nation or network. Your local, federated records must often be mapped to, or validated against, this central registry.

When an user has given consent to register the alias externally, there’s an extra step before the system finalizes the anchor locally, it calls the third-party to confirm or register the alias at a broader level.

- If the third party accepts the alias, local creation proceeds no duplicates or conflicts.
- If the third party rejects (duplicate alias, missing data, etc.), the process is stopped, and no anchor is created.

## Co-existence and Mapping

In many regulated environments, the two models must co-exist. The Minka Ledger is designed to handle this co-existence by managing the local Federated Directory while providing integration mechanisms for a Centralized Directory.

You must handle scenarios where an alias exists in one system but not the other, or where the central system must validate the creation or lookup of a local Anchor record.

This complex interaction ensures that:

- Your local system (Federated Directory) remains fast and authoritative for your customers.
- All transactions comply with the rules and data requirements of the national Centralized Directory.
