This tutorial teaches you how to manage an existing Alias (which is an Anchor record). You will learn how to use the Minka CLI or the API to update its status or custom data in the Ledger.

## Pre-requisites

Before you begin this tutorial, ensure you have the following in place:

    - **API Access:** You have the base URL for the Ledger's API `/v2`
    - **Signer Setup:** You have an authenticated Signer identity and the necessary private key for signing requests.
    - **Existing Alias Handle:** You must know the Alias Key of the Anchor record you intend to modify or delete.
    - **Authorization:** Your Signer must have the necessary permissions (defined by Policies and Circles) to execute `PUT` and `DEL` operations on Anchor records.

    <Callout type="info">
    For information on setting up your Signer and the security protocols, see Authentication and Security Basics.
    </Callout>

## Update an Alias Record 
    
    ### Update using the Minka CLI
    The Minka CLI provides an interactive prompt to help you build the update payload. It automatically handles fetching the latest record, signing the new payload, and submitting the request.

        1. Run the `minka anchor update` command, specifying the alias you want to change:
        
        ```bash
        minka anchor update <alias-handle>
        # Example: minka anchor update carlos6@minka.io
        ```

        2. The CLI will prompt you to select which fields you want to update (e.g., custom_data, status).
        3. Confirm the changes and provide your Signer credentials when prompted.

    ### Update using the API
    You can manually construct and send a `PUT` request to the `/v2/anchors/{handle}` endpoint, using the unique alias key to modify the existing Anchor record.

## Execute the Update

    1. **Construct the Payload:** Define the fields you want to change in the request body. You can update the alias's status and custom data simultaneously.
    2. **Sign the Request:** Use your private key to cryptographically sign the entire `PUT` request payload.
    3. **Submit the Request:** Send the signed request to the Ledger.

 ## Anchor Update Behavior and Context

    ### Simultaneous Updates
     The `PUT` operation handles both data changes and status changes, allowing you to update both non-critical custom data (like the owner's name) and the operational status simultaneously in a single request body.

     For instance, you can submit a request body to change the `owner_data` while simultaneously setting the `status` field to `suspended`. 
 
     ### Sync Update check
    In addition to transactional changes, thie `PUT` operation is also used to perform a sync update check in integrated environments. This is a mechanism where a client validates that their local record state matches the latest state recorded in the Ledger.


    ### Third-Party Integration and Validation
     In regulated environments that require Third-Party Integration (e.g., a Centralized Directory like DICE), the Ledger performs additional steps after receiving your signed request. 
    
    This may include third-party validation and adding compliance-required Timestamps to the record before the update is finalized. You only need to submit the request; the Ledger handles the compliance workflow.
