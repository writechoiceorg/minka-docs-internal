The Alias Directory is a key component of a regulated real-time payment (RTP) environment. It simplifies payment initiation by letting users use simple, human-readable aliases such as phone numbers, email addresses, or ID numbers instead of complex account details.

You securely map each alias to a financial account. You register this mapping as an **anchor** (a foundational ledger record that securely links an alias to a financial account) on Minka's ledger infrastructure.

The Alias Directory is built on a few core concepts:

- **Handle**: The alias identifier itself (e.g., tel:+15551234567 or email:user@example.com).
- **Target**: The financial account associated with the alias that the alias maps to for transaction routing.
- **Anchor**: The foundational ledger record that securely and immutably links the Handle to the Target. Anchors store this linkage and associated metadata but do not hold balances.
- **Custom Data**: Optional metadata linked to the account or its owner, such as name or other domain-specific fields.
- **Labels**: A set of key-value tags used for regulatory and institutional identification, such as participant codes or document numbers.

## High-Level architecture

The Minka Alias Directory Solution is built on top of the Minka Ledger and manages aliases in a secure, auditable system that supports multiple participants.

The solution involves three main areas:

- **Participant Ecosystem**: This includes your end-users interacting with your digital channels (apps or portals), your core banking systems, and a secure middleware bridge. The bridge signs and sends requests to the Minka ledger.

- **Alias Directory Solution**: This provides the core services of Anchors API to manage alias records. It also exposes metrics and logs for audits and operational insight, and broadcasts alias-related events (e.g., create, update) to subscribers in real time.
- **Support & Monitoring**: Includes a graphical UI (Studio) for support staff to securely query and manage anchors.

The system authorizes all operations via JWT (JSON Web Token) tokens and digitally signs them, ensuring every change is tamper-evident and fully auditable on the ledger.

## Architectural Models
The Alias Directory's architecture is flexible, supporting both decentralized and centralized requirements depending on the ecosystem's needs:

The Federated Directory model lets each participating financial institution manage its own local set of aliases for its customers directly within the Minka Ledger environment.

Conversely, the Centralized Directory model integrates with an external, authoritative third-party registry. This integration is vital to ensure an alias is unique across the entire financial ecosystem and to allow payments between customers of different institutions.

Read more about these models in the [Federated and Centralized Alias Directories](/docs/alias-directory/fed-cen-dir) page.

## Working with Aliases
The Alias Directory provides an API to manage the lifecycle of an alias.

- **Register and Link Aliases:** You register a new payment recipient by creating an Anchor record. This action links a simple Alias Key to the recipient's secure Payment Credentials.
- **Look Up Account Information:** The primary function of the Directory is to resolve an alias. When you need to send a payment, you look up the recipient using their Alias Key to retrieve the necessary Payment Credential. You then confirm the transaction with the user before proceeding.
- **Manage the Alias Lifecycle:** You maintain data integrity and compliance by managing the status and information associated with each Anchor record throughout its life.
